CrowdGuard Command — Agent Architecture

Which orchestration approach fits best for the finale? Pick the one you want to build.

A

Hierarchical Orchestrator + Specialists

One master Orchestrator Agent receives all events and delegates to specialist agents. Each specialist acts independently and reports back.


Sensor Data / Operator Input
    ↓
[ Orchestrator Agent ]
  ↙   ↓     ↓     ↘
[Crowd] [Route] [Threat] [Emergency]
    ↓     ↓     ↓       ↓
[ Unified Dashboard + Action Log ]

  • Clean separation of concerns
  • Easy to demo each agent independently
  • Orchestrator can run parallel sub-agents (ADK ParallelAgent)
  • Best for Phase 2 Q&A defense
B

Event-Driven Pipeline (Sequential)

Data flows through a fixed pipeline: Ingest → Analyze → Decide → Act. Each stage enriches the data and passes it forward.


Sensor Feed
    ↓
[ Crowd Density Agent ]
    ↓ (density + flow vectors)
[ Routing Decision Agent ]
    ↓ (gate commands)
[ Threat Evaluator Agent ]
    ↓ (risk score)
[ Emergency Protocol Agent ]

  • Simple to reason about data flow
  • Bottleneck if one agent is slow
  • Less "agentic" — more like a pipeline
  • Lower score on "Agentic Depth"
C

Hybrid: Parallel Monitoring + Sequential Response

Monitoring agents run in parallel continuously. When a threshold is crossed, a sequential response chain activates.


[ Always-On Parallel Monitor ]
[Crowd] + [Gate] + [Weather] (concurrent)
    ↓ threshold breach
[ Orchestrator triggers Response Chain ]
    ↓
Route → Escalate → Notify → Log

  • Most realistic to real stadium ops
  • Shows ADK ParallelAgent + SequentialAgent
  • Highest "Agentic Depth" score potential
  • Recommended — mirrors your existing CrowdGuard pattern
